# 支持品項：把別人的心願清單放進自己的清單

日期：2026-11-01

## 目的

有影響力的人（網紅、明星）想用自己的影響力幫助公益事件。例如某地發生天災，慈善組織正在募款或徵求物資，這位網紅就在自己的心願清單放一個品項，內容是「完成這個組織的清單」。粉絲從網紅的分享頁點進組織的清單捐助，網紅則看得到自己帶來多少成果。

同一機制也適用於個人清單：任何人都能把另一個人的公開清單當成自己的心願。

## 使用者決定

- 品項指向別人的**整份清單**，對象是組織或個人的公開清單，第一版兩者都做。
- 錢和物資直接到對方清單，發起者完全不經手。品項本身不收款，只是入口。
- 品項可以不設日期。
- 只有粉絲從品項點進對方清單**並完成捐助**才算有效，只開頁面不算。
- 成果公開：看得到品項的人都能看到累計數字。
- 成立不需要對方同意，只發站內通知，不寄 Email。

## 名詞

- **支持品項**：`funding_mode = 'support'` 的品項。
- **發起者**：建立支持品項的人。
- **對方清單**：品項指向的清單。
- **帶來的成果**：透過這個品項完成、目前仍有效的捐助。

## 非目標

- 不做金額目標與進度條。支持品項沒有目標，只有累計數字。
- 不連到對方清單裡的單一品項。
- 不把金額和物資件數換算或合併。
- 不做排行榜、發起者之間的比較。
- 不做跨裝置歸因。
- 不新增「有新捐助」通知（D58），成果只在頁面上呈現。

## 不可出現的結果

- 任何頁面、API、通知透露**誰**透過品項捐助。對外只有彙總數字。
- 對方清單改成非公開後，發起者的公開頁還顯示它的名稱、封面或連結。
- 支持品項被當成一般品項認捐或贊助。
- 歸因驗證失敗導致捐助失敗。歸因不成立時捐助照常完成，只是不計入。
- 驚喜模式的清單因為公開數字而提前被受贈者知道有人送禮。

## 行為規則

### 建立支持品項

- 發起者在品項編輯面板選擇「支持一份清單」，貼上分享連結或輸入 slug，系統帶出對方清單的名稱供確認。
- 品項只有標題由發起者撰寫，預設填入對方清單名稱。
- 建立當下對方清單必須可公開提供，也就是 `/public/wishlists/{slug}` 能回內容的狀態（公開、上線、未下架，組織據點另須符合 `LIVE_SITE`）。否則回 422，訊息不區分「不存在」和「不公開」，以免探測清單是否存在。
- 不可指向自己擁有或可管理的清單（`can_manage_wishlist`）。**（我的決定）**
- 支持品項建立後，目標清單不可改。要換對象就刪掉重建，避免舊成果被掛到新對象上。**（我的決定）**
- 既有品項不可轉成支持品項，支持品項也不可轉成別種模式。**（我的決定）**
- 支持品項可以放在任何可見性的清單，包含組織自己的清單和據點，權限沿用 `can_manage_wishlist`。公開數字的範圍就是看得到這個品項的人。**（組織清單是我的決定）**

### 顯示

- 品項卡顯示標題、對方名稱與封面、「透過這裡籌到的點數」「透過這裡認捐的物資」、「前往支持」按鈕。樣式見本文件定稿前的草圖方案 A。
- 不顯示進度條、百分比、截止日，也不套用 `No.XX` 右側的百分比。
- 對方名稱與封面**每次讀取時即時取得**，不留快照；對方不再可公開提供時回 `ended: true` 且不帶名稱、封面、slug。
- 已結束時品項改顯示「已結束」和累計數字，不再帶人過去。品項自身的標題是發起者寫的，繼續顯示。
- 對方是鎖定中的驚喜清單（`surprise_locked`）時，數字回 `null`，按鈕照常運作；對發起者本人也一樣。解鎖後才顯示。**（我的決定）**
- 發起者的清單已關閉時隱藏按鈕，數字保留。

### 歸因

- 粉絲點「前往支持」，連到 `/s/{對方 slug}?via={支持品項 id}`。
- 前端把 `{對方 slug → (item_id, 時間)}` 存進 localStorage，保留 7 天。以 slug 為鍵，因為分享頁本來就有 slug，公開回應不需為此多帶 id。**（7 天是我的決定，要涵蓋登入、儲值和 ATM 隔日入帳）**
- 同一份對方清單只保留最後一次點入的品項，所以同一筆捐助不會重複計算。**（我的決定）**
- 登入導向要保留 `via` 查詢參數。
- `POST /items/{id}/claims` 和 `POST /items/{id}/contributions` 增加選填的 `via_item_id`。
- 後端在交易外驗證：該品項存在、未刪除、`funding_mode = 'support'`、指向的清單就是這筆捐助所屬的清單。不成立時以 `NULL` 寫入，不回錯誤。
- 歸因在捐助建立時定案。之後修改數量不改歸因；已有的捐助不會因為後來才點連結而被歸因。**（我的決定）**
- 發起者自己的捐助一樣計入，因為是真實的捐助。**（我的決定）**
- 7 天只在前端判斷。有人繞過前端直接帶參數，也必須實際花錢或認捐才會增加數字，所以不做伺服器端點擊紀錄。

### 帶來的成果怎麼算

讀取時即時彙總，不存快取欄位：

- 點數：`contributions` 中 `via_item_id = 品項` 且狀態為 `pledged`、`captured` 的 `points - refunded_points` 總和。
- 物資：`claims` 中 `via_item_id = 品項` 且狀態為 `reserved`、`purchased`、`delivered` 的 `qty` 總和。
- 退款、撤回、逾期釋放後數字自動減少。
- `reallocate` 產生的新 contribution 要沿用原本的 `via_item_id`，金額仍留在對方清單裡，因此繼續計入。**（我的決定）**
- 帳號刪除會取消 reserved 認捐，數字會隨之下降；彙總不帶身分。

### 通知

- 新 kind `wishlist.supported`：Social 分類，`email_tier = InAppOnly`，不寄信、不推播。
- 收件人：個人清單是擁有者；組織清單是該組織所有有效的 owner 和 coordinator。**（我的決定）**
- 內容：「{發起者暱稱} 把你的清單「{清單名稱}」放進了他們的願望」，連到對方自己的清單管理頁，不連發起者清單。發起者清單可能不公開，連結會打不開。
- 發起者的清單已發佈時，新增支持品項就通知；草稿內的支持品項等發佈時補發。同一個支持品項只發一次。**（我的決定）**
- 建立支持品項每人每小時 20 次，避免用通知騷擾別人。**（數字是我的決定）**

### 對方的控制權

對方不能移除別人的支持品項。不想被連結時可把清單改成非公開，品項就會變成已結束；有騷擾可走既有檢舉。**（我的決定，符合「不需同意」，日後需要再加移除功能）**

## 資料

新增 migration，編號用實作時下一個可用的號碼（目前 main 到 0054，其他分支可能占用 0055）：

- `ALTER TYPE funding_mode ADD VALUE 'support'`。enum 新值不能在同一交易使用，CHECK 條件要以 `funding_mode::text` 比對，或拆成兩個 migration。實作時逐條檢查 `wishlist_items` 既有 CHECK，確認 `support` 模式的價格、數量、目標欄位能通過。
- `wishlist_items.support_wishlist_id uuid REFERENCES wishlists(id) ON DELETE SET NULL`，加 CHECK：非 support 品項必須為 NULL。對方清單被硬刪時為 NULL，視同已結束。
- `wishlist_items.support_notified_at timestamptz`，避免重複通知。
- `contributions.via_item_id uuid`、`claims.via_item_id uuid`，**刻意不加外鍵**，理由同 0050：外鍵檢查會對另一份清單的品項加 KEY SHARE 鎖，把發起者的品項捲進對方清單的鎖序。
- 兩張表各加部分索引 `WHERE via_item_id IS NOT NULL`。

選用新 enum 值而非旗標，因為 `claims.rs` 的 `funding_mode = 'quantity'`、`contributions.rs` 的 `funding_mode = 'crowdfund'` 條件會自動擋掉對支持品項的捐助。

## 要特別處理的地方

- **`ELSE` 當數量品項的程式碼**：`wishlists.rs` 的 `CLAIMED_SQL`、`OPEN_SQL`，`public.rs`、`profiles.rs`、`friends.rs` 的需求數加總，`public.rs` 救災事件的急需統計，`dashboard.rs` 與 `progress.vue` 的進度，都把非 crowdfund 視為數量品項。支持品項不可算進「需要 / 已認捐」，否則清單永遠不會顯示完成。
- **快取**：`public.rs` 的 ETag 只看 `wishlists.updated_at`，對方清單上的捐助不會改變它，數字會卡在 304。含支持品項的清單改回 `public, s-maxage=10`，不帶 `stale-while-revalidate`，也不帶 ETag。公開數字與對方名稱最多延遲 10 秒，流量高峰仍由 CDN 擋下，不做即時推送。
- **不做連動清除快取**：對方清單不再公開時，不清除發起者清單的快取，10 秒內自然過期。這取代原本的 `cdn::purge_wishlists` 連動，因為它要改 12 個呼叫點，其中多處被 `scripts/mutate.py` 以原文定位。**（我的決定）**
- **`GET /public/wishlists/{slug}`** 不可讀 cookie，支持品項的彙總不依觀看者而異，可以放進公開回應。
- **靈感頁**：`inspire.rs` 依 `catalog_ref` 列品項，支持品項沒有 `catalog_ref`，不受影響。專案內只有 `item_create` 會新增品項，沒有複製品項的功能。
- **新手導覽**：支持品項算作 `item` 步驟完成，不需額外處理，但要確認文案不矛盾。

## 併發

`support_wishlist_id` 的外鍵會對目標清單加 KEY SHARE，與 `FOR UPDATE` 短暫互等，已確認 item_delete、archive、帳號刪除沒有死鎖環。歸因驗證在交易外、彙總只讀，沒有更動既有鎖序，因此不需新增 `scripts/mutate.py` 的 mutant。實作若改成在交易內鎖對方清單，就要補。

## 測試重點

- 從品項點入後贊助與認捐都計入；未帶 `via`、`via` 指向別份清單、`via` 是已刪除品項時捐助成功但不計入。
- 撤回、退款、逾期釋放、`reallocate` 後數字正確。
- 兩個支持品項指向同一清單時，只算最後點入的那個。
- 對方清單改私人、下架、刪除、組織撤銷認證時，公開回應不含對方任何資訊。
- 鎖定中的驚喜清單數字為 `null`。
- 對支持品項認捐或贊助被拒絕。
- 含支持品項的清單需求數、完成狀態、救災急需統計不受影響。
- 通知只發一次、內容無捐助者身分、不寄 Email。
- 匿名訪客的公開回應不含 `via` 相關的捐助者資料，回應不因觀看者而異。

## 已知限制

- 歸因存在瀏覽器裡。粉絲換裝置、清除資料，或從 App 內建瀏覽器切到外部瀏覽器，就不會計入。這符合「從品項點入」的定義，但實際數字可能略低於真實影響力。
