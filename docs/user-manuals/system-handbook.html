1. 系統概覽

Wishly（心願同步）解決「想要的人說不出口、想送的人怕重複」。建立者列出品項與數量，用一條連結分享到 LINE / FB / 簡訊；朋友點開即可瀏覽，不必安裝；認捐時需登入（D50），登入後回到原品項即可完成。系統保證同一品項不會被超額捐助，並即時更新完成度。

建立者  建清單 → 加品項 → 發佈 → 複製連結傳到群組
訪客    點連結 → 看清單（免登入）→ 登入 / 註冊 → 回原品項捐助（D50：認捐需登入）
系統    條件式 UPDATE 防超賣 → SSE 即時推播 → Email 通知建立者
大件品  登入使用者以「點數」多人湊 → 達標後平台代購寄出

2.4 兩種身分

  • 創建者：cookie ws_session（30 天）。資料庫只存 SHA-256 雜湊。原生殼不送 cookie，改用 Authorization: Bearer，與 cookie 共用同一張 sessions。
  • 訪客（legacy，D50）：僅用於管理 D50 前既有的訪客認捐，不能新增認捐或增量；X-Guest-Token header 優先，其次 ws_guest cookie（1 年，HttpOnly）。後端只存雜湊；前端同時把權杖放 localStorage 當備援（LINE 內建瀏覽器 cookie 不穩）。
  • 認捐一律需登入（D50），以帳號名稱進行，不再問暱稱，並可設定該筆捐助的公開層級；未登入呼叫 POST /items/{id}/claims 回 401 且不寫入任何資料。
  • 明確以 header 帶失效訪客權杖回 401；只有 cookie 帶的失效權杖視為匿名，避免舊 cookie 永遠擋住捐助。

3. 本機快速開始

  1. 啟動相依服務 
    docker compose up -d      # PostGIS、MinIO（模擬 R2）、Mailpit（OTP 信 http://localhost:8025）
  2. 啟動後端 
    export DATABASE_URL=postgres://wishly:wishly@localhost:5432/wishly
export APP_ENV=dev        # 必設；未設視為 production，缺機密會拒絕啟動
cargo run --manifest-path apps/api/Cargo.toml     # http://localhost:8080，啟動時自動套用 migration
    沒裝 Rust 可用 scripts/cargo.sh test（Docker，較慢）。
  3. 啟動前端 
    cd apps/web && npm install && npm run dev     # http://localhost:3000
  4. 註冊一個帳號：到 /register，驗證碼從 Mailpit（http://localhost:8025）取得。
  5. 成為 staff（需要後台時） 
    docker compose exec db psql -U wishly -d wishly -c "UPDATE users SET is_staff = true WHERE email = 'you@example.com';"
只想看訪客畫面？node mocks/server.mjs 在 :8080 啟動訪客端契約 mock（slug：demo / closed / gone / boom / sseoff），不需後端與資料庫。

4. 創建者操作手冊

4.1 註冊與登入

Email ＋ 密碼

  1. 到 /register，填顯示名稱、Email、密碼（至少 8 字元）。
  2. 系統寄出 6 位數驗證碼（10 分鐘內有效，最多嘗試 5 次）。輸入後帳號建立並自動登入。
  3. 日後到 /login 用 Email 與密碼登入。登入成功導向 /dashboard（或 redirect 參數指定的頁面）。
  • 同一 Email 每小時最多寄 5 封驗證碼，兩封之間至少間隔 60 秒（登入 / 註冊 / 重設共用）。
  • 寄驗證碼階段不論 Email 是否已註冊都回成功（不洩漏帳號是否存在）。輸入驗證碼後，只有該 Email 的登入方式已有密碼才回 EMAIL_EXISTS（請直接登入或用「忘記密碼」）；已有帳號但尚無密碼者，可藉此流程完成密碼設定。
  • 登入失敗：同一 Email＋IP 15 分鐘內 5 次即鎖定；同 Email 跨 IP 累計 20 次、同 IP 累計 30 次也會鎖定（回 429，建議 5 分鐘後再試）。成功登入或重設密碼會清除該 Email 的失敗紀錄。

忘記密碼

到 /forgot-password 輸入 Email，收驗證碼後設定新密碼。重設成功會登出所有裝置。沒有已驗證 Email 的帳號（例如只用 LINE 登入）無法用此方式找回。

Google / LINE

登入或註冊頁的「使用 Google 繼續」「使用 LINE 繼續」。若 Google 提供的 Email 已驗證且與既有帳號相同，會自動連結到該帳號。原生版（Tauri）同樣提供：以系統瀏覽器完成登入（PKCE），再由 deep link 返回 App。

4.3 管理品項

在 /lists/{id}/edit 按「＋ 新增品項」，品項欄位：

欄位說明 / 限制
名稱必填，至多 120 字
品牌 / 規格 / 商品網址選填（100 / 200 / 2000 字）；訪客看到「商品連結」（rel="noopener nofollow"）
圖片選填；上傳後先為「處理中」，後端去除 EXIF / GPS 並重新編碼後才顯示。未通過會標示「圖片未通過，請換一張」
優先度高 / 中 / 低（預設中）
取得方式數量捐助：設「需要數量」1–99、可填參考價格
心願眾籌：設「目標點數」（1 點 = NT$1）與「募集截止」，需先填收件資訊，見下方
  • 排序：品項卡片的 ↑ ↓ 按鈕調整順序；訪客端會把「已被捐助完」的品項排到最後。
  • 修改數量：不可低於已被捐助的數量（QTY_BELOW_CLAIMED）。驚喜鎖定期間不能調降數量。
  • 刪除品項：若已有捐助，第一次刪除會提示；再按一次「連同捐助一併刪除」會取消這些捐助。驚喜鎖定期間不能刪除品項。已有認捐的眾籌品項刪除時，pledged 的點數會退回捐贈者錢包並通知。
  • 取得方式一旦有人捐助 / 贊助就不能切換；眾籌達標或截止後不能改目標與期限。
  • 並行編輯保護：儲存時會帶 expected_updated_at；若資料已被其他地方修改，回 STALE_VERSION，畫面會提示「重新載入」。

眾籌品項與收件資訊

眾籌達標後由平台代購並寄出，所以含眾籌品項的清單必須先填「收件資訊」（編輯頁的摺疊區塊）：收件人 1–50 字、電話 6–20 碼（可含 + - 空白）、地址 5–200 字。

  • 收件資訊在伺服器端以 XChaCha20-Poly1305 加密後儲存，只有清單擁有者與負責下單的營運人員能看；朋友永遠看不到。
  • 為了隱私，已儲存的內容只顯示遮罩值，要修改須重新輸入完整三個欄位。
  • 未填收件資訊就新增眾籌品項或發佈，會回 SHIPPING_ADDRESS_REQUIRED，介面會引導你填寫。
  • 眾籌品項的數量固定為 1，由平台代購（concierge）。

4.5 驚喜模式

適合生日 / 婚禮：活動日之前你只看得到整體完成度，看不到誰送了什麼，保留驚喜。

  • 建立時必須填未來的活動日。鎖定持續到活動日當天 00:00（台北時間）。
  • 鎖定期間：進度頁只顯示整體完成度與倒數；各品項進度顯示「進度已隱藏」；捐助者資訊不可見；匯出資料中的各品項捐助數為空；通知信只寫「有 N 件新捐助」，不含品項與捐助者。
  • 鎖定期間不能關閉驚喜模式、不能刪除品項或調降數量；你只能在解鎖後標記「已送達」或取消捐助。
  • 眾籌品項的完成度只在「達標」那一刻跳動，不會隨每筆認捐洩漏進度。
  • 已知限制（契約 D4）：公開頁仍回傳 x/y，由前端對建立者本人做軟性遮罩；技術上能繞過的是建立者本人的瀏覽器，不是其他訪客。

  3. 發佈成功後出現「分享你的清單」視窗：複製連結、用 LINE 傳、簡訊、Facebook，或讓朋友掃 QR code。

4.7 追蹤進度

/lists/{id}/progress 會即時更新（SSE；連續失敗 2 次自動改為定時輪詢，畫面顯示「即時更新中」或「定時更新中」）：

  • 整體完成度長條、完成項數、數量與點數進度。
  • 數量型品項：每筆捐助的捐助者、數量、留言；可「標為已送達」或「取消捐助」（取消會把數量釋出給別人）。
  • 眾籌品項：已募 / 目標、截止時間、捐款者名單（匿名者顯示「匿名朋友」）、採購進度（狀態、物流單號、下單 / 出貨 / 送達時間）、因實際花費較低而退回的差額。
  • 最下方有「眾籌採購彙總」：已達標、已下單、運送中、已送達的項數。
  • 進度頁的捐助明細只有姓名、數量、狀態、留言與時間；訪客選填的聯絡方式目前不會顯示在進度頁。

收到通知：訪客捐助後第一封即時寄出，之後同一清單的新捐助合併為每日台北 09:00 的彙整信。在「帳號設定 → 通知」可關閉，或點信中的一鍵退訂連結。

5. 訪客與贊助者手冊

5.1 登入後認捐

D50（2026-10-18）：訪客僅能瀏覽，認捐需登入產品負責人決定：認捐需要消耗點數，未登入無法紀錄點數。目前數量認捐本身並未扣點數（只有心願眾籌扣點），此規則先讓認捐綁定會員身分。
  1. 點開朋友分享的連結（/s/{slug}）。看得到清單標題、說明、完成度與各品項。受限清單可能要求登入或輸入密碼。
  2. 在想送的品項按「我要送」；未登入時按鈕為「登入後認捐」，登入或註冊後會回到原品項。選數量（1–99，不超過剩餘量）。
  3. 可選填留言（至多 200 字）與這筆捐助的公開層級；不再填暱稱、聯絡方式或 Email，名稱採帳號名稱。
  4. 按「確認捐助」。成功後出現「✓ 捐助成功！」畫面。
  • 瀏覽免登入、認捐需登入；可選這筆捐助的公開層級（公開 / 僅好友 / 私人）。
  • 不會超賣：兩人同時搶最後一件，只有一人成功，另一人看到「抱歉，只剩 N 個了」或「剛剛被別人捐助完了」。
  • 同一品項只能有一筆有效捐助；再次捐助會自動切換成「修改我的捐助」。
  • 建立者不能捐助自己的清單。已結束的清單不再接受捐助。
  • 網路不穩重送是安全的：同一份捐助使用同一把 Idempotency-Key，重送不會重複扣量。
在 LINE 內建瀏覽器登入狀態存放在瀏覽器儲存空間，LINE 關閉後可能需重新登入；可點右上角「⋯」→「用預設瀏覽器開啟」。會員的捐助綁定帳號，換裝置登入即可管理。以下「換裝置找回」僅適用 D50 前的舊訪客捐助。

5.2 管理我的捐助（/me/claims）

已捐助 reserved→已購買 purchased→已送達 delivered
  • 捐助後可按「標記已購買」「標記已送達」；「取消」可在送達前隨時使用（目前取消不會寄通知信給建立者，只有進度頁的即時刷新）。取消後數量立即歸還給其他人。
  • 可調整這筆捐助誰看得到（僅登入者）；舊訪客捐助（D50 前）可改暱稱，可減量、取消，但不能增加數量（須登入）。
  • 「過去的紀錄」收納已取消 / 已逾期的捐助。
  • 換裝置找回（舊訪客捐助）：確認信中的「管理我的捐助」連結是一次性、30 天內有效的恢復權杖；使用後會換發新的訪客權杖。失效時回清單連結或聯絡客服。

5.3 心願眾籌（眾籌品項）

眾籌品項顯示「已募 X / 目標 Y 點」與進度條。贊助需要登入（未登入會導向登入頁，登入後回到本頁）。

  1. 在眾籌品項按「心願眾籌」，輸入點數（1 到剩餘額之間的整數；可按「剩餘全額」）。
  2. 選填留言（至多 200 字）、勾選「匿名贊助」（頁面顯示為「匿名朋友」）、選這筆贊助誰看得到。
  3. 確認後點數從錢包扣出，狀態為 pledged（認捐中）。餘額不足會顯示還缺多少。
  4. 達標的那一刻，所有 pledged 轉為 captured，平台建立採購單；你會收到 Email 通知，之後依序收到出貨、送達通知。
點數 1 點 = NT$1點數只能用在心願品項，不會轉成現金給建立者，也不可轉讓。儲值款項屬預收款，依退款規則辦理。

如何儲值（/me/topup）

在「我的點數」頁按「儲值」。若顯示「儲值功能尚未開放」，代表營運尚未啟用金流，點數仍由平台發放。原生 App 內無法開啟付款頁，請改用網頁版。

  1. 選金額：快選 500 / 1,000 / 2,000 / 5,000，或自訂 100 到 50,000 的整數。錢包（含待付款的儲值單）合計不可超過 50,000 點；新帳號另有每日上限，超過時會顯示今日還能儲多少。
  2. 選付款方式：信用卡（30 分鐘內完成）；超商代碼、超商條碼、ATM 虛擬帳號（皆 3 天內繳費）。
  3. 選發票載具：預設會員載具；也可填手機條碼（/ 加 7 碼大寫英數）、自然人憑證（2 碼大寫英文加 14 碼數字）、捐贈碼（3 到 7 碼數字）或公司統編（8 碼）。格式錯誤會在該欄位提示。
  4. 確認摘要後按「前往付款」，頁面會跳到綠界付款頁；信用卡在該頁輸入卡號（卡號不經過本站）。
  5. 超商代碼：回到「儲值紀錄」查看繳費代碼（可按「複製」），到超商機台輸入代碼列印繳費單，在期限內到櫃檯付款。超商條碼：紀錄中會顯示三段條碼，列印或出示給店員掃描繳費。ATM：紀錄中顯示銀行代碼與虛擬帳號，用 ATM 或網路銀行轉帳。剛建單時可能先顯示「取號中…」，數秒後自動出現；若一直沒出現，按「重新整理」。
  6. 付款完成後點數會在數秒到數分鐘內入帳（超商與 ATM 依繳費時間），入帳時頁面會顯示成功與新餘額。逾期未付的單會顯示「已逾期」，請重新建立。

如何申請現金退款（/me/refund）

只有儲值購買的點數可以退回現金；禮物卡與贊助取得的點數不可退。在「我的點數」頁，當「可退現金」大於 0 時會出現「申請現金退款」按鈕；沒有可退點數時，頁面只會說明原因，不顯示表單。

  1. 按「申請現金退款」，頁面上方顯示目前可退現金餘額（點）。
  2. 輸入要退的點數（整數，至少 1、不超過可退餘額，單次上限 50,000），或按「全部」帶入可退餘額。
  3. 確認摘要：點數會先從錢包扣除，審核通過後退款；若申請被拒絕，點數會退回錢包。
  4. 按「送出申請」。送出中按鈕會停用，網路失敗後重試不會重複建立申請。成功後會顯示扣除的點數與新餘額，申請出現在下方「我的申請」。
  5. 狀態：待審核、處理中、已退款、已拒絕（會顯示拒絕原因，點數已退回錢包）。有待審核或處理中的申請時，頁首會顯示「審核中」。

可能看到的提示：「可退現金的點數只有 N 點」（金額超過可退點數，請調降）；「點數餘額不足」；「申請太頻繁」（每人每小時最多 10 次，請稍後再試）；「帳戶已凍結，暫時無法申請現金退款，請聯絡客服」（錢包凍結時整個表單隱藏）。

我的點數（/me/wallet）

  • 可用點數、認捐中點數；錢包被凍結時顯示「已凍結」與提示（錢包、儲值、退款頁都會顯示），不能新增贊助或申請現金退款，但退點仍會入帳。
  • 撤回：品項達標前（仍為 pledged）隨時可撤回，點數立即回到錢包。已達標（captured）則回 CONTRIBUTION_LOCKED。
  • 轉投：只在來源品項已截止未達標（expired）且仍在 7 天選擇期內時可用；目標須是同一份（使用中）清單另一個募集中、尚未截止的眾籌品項，且須能承接整筆點數（不超過其剩餘額）。不異動錢包；原認捐標為 reallocated 並建立一筆新認捐。
  • 截止未達標：品項變為 expired，有 7 天選擇期讓你撤回或轉投；逾期未處理則自動退回錢包。
  • 差額退回：實際採購金額低於目標時，差額依各 captured 認捐的點數比例（最大餘數法，總和恆等於差額）退回。
  • 採購失敗 / 取消：已扣用的點數全額退回，並通知捐贈者。
  • 點數帳本列出每筆異動與當時餘額，只增不改。
  • 每個帳號每分鐘最多 30 次認捐操作。

5.4 檢舉清單

清單頁底部「檢舉此清單」，不需登入。選原因（疑似詐騙 / 不當內容 / 侵害著作權 / 洩漏個人資料 / 其他）、補充說明（選填，至多 500 字），完成 Turnstile 人機驗證後送出。我們由人工審核，不會告知建立者是誰檢舉。同一 IP 每小時最多 10 次、對同一清單每天 1 次。

6. 營運後台手冊 STAFF

入口 /admin（儀表板右上「後台」按鈕，僅 staff 可見）。非 staff 回 403 STAFF_ONLY。後台所有寫入動作都會寫入 audit_logs（actor_type = staff）。

6.1 成為 staff 與兩步驟驗證

  • 第一位 staff 必須在資料庫設定：UPDATE users SET is_staff = true WHERE email = '…';。之後可在後台「使用者」分頁設為 / 取消 staff。
  • 最後一位有效 staff 不可被停權、降權，也不可自行刪帳號。
  • 啟用 TOTP（/admin/mfa）：用驗證器 App（Google Authenticator、1Password 等）掃 QR code，輸入 6 位數碼完成啟用（RFC 6238：SHA-1、6 碼、30 秒）。啟用後每次登入後台都須先通過驗證；5 分鐘內最多嘗試 5 次。
  • 未啟用 TOTP 的 staff，後台首頁會顯示建議啟用的提示。
  • 手機遺失：請另一位 staff 在「使用者」找到你，按「重設兩步驟驗證」。若沒有其他 staff，見 11.6。

6.2 營運概況

顯示使用者數、清單總數、使用中清單、已下架清單、待處理檢舉；展開可看捐助狀態、通知狀態與最近 7 天稽核動作分佈。

6.3 檢舉佇列與下架

  1. 「檢舉佇列」預設顯示待處理；可切換已處理 / 已駁回。
  2. 點清單連結開公開頁檢視（下架後 staff 仍可從後台找到）。
  3. 按下架：必填下架原因（至多 200 字，會顯示給建立者）。下架後公開頁、SSE、檢舉端點都回 410 WISHLIST_REMOVED，且回應不含原因，並清除 CDN 快取。
  4. 按已處理 / 駁回 結案檢舉。
  5. 「清單搜尋」可用 slug 或建立者 Email 前綴、清單狀態、下架狀態篩選，並可對任一清單「恢復上架」。

6.6 點數錢包（/admin/wallets）

6.7 系統旗標與唯讀模式

「系統旗標」分頁目前只有 read_only。開啟後，全站所有非安全方法（POST / PATCH / PUT / DELETE）回 503 READ_ONLY_MODE，例外（放行）：登入、登出、登入 OTP、兩步驟驗證、後台旗標操作，以及退訂 POST /unsubscribe。用於資料庫維運或事故止血。開啟 / 關閉都需二次確認，並寫入稽核。

6.8 稽核紀錄（/admin/audit）

可用操作者 UUID、動作、對象類型（須完整匹配）、對象 UUID、起訖日期查詢；日期以台北時區計算且包含結束日。每筆可展開「操作內容」(diff)。

6.9 現金退款審核（/admin/cash-refunds）

使用者申請時點數已先扣除（只扣可退現金的儲值批次）。後台首頁按「現金退款」進入；預設只看待審核，可改選全部 / 處理中 / 已退款 / 已拒絕。每列顯示使用者、Email、退款點數、申請與完成時間、拒絕原因。

  1. 待審核的申請按「開始處理」（requested → processing），確認對話框按同名按鈕送出。
  2. 到金流商後台完成原路退款（本系統不代為呼叫金流商）。
  3. 回到列按「標記已退款」（processing → completed）。此動作無法復原，確認文字會寫明使用者與金額。
  4. 無法退款時，待審核或處理中的申請都可按「拒絕並退點」：拒絕原因必填（空白會被擋下；原因會顯示給使用者），點數依原批次退回使用者錢包。已退款 / 已拒絕的列沒有動作按鈕。

他人已先處理時回 INVALID_STATE_TRANSITION：頁面會關閉對話框、重新載入列表並顯示說明。所有處理都寫入稽核（cash_refund.process）。

6.10 拒付欠款（/admin/wallet-debts）

信用卡拒付敗訴後，該筆儲值已被花掉而扣不回的點數會記為欠款。預設列出未結清，可切換已追回 / 已核銷。每列顯示使用者、欠款點數、對應儲值單、建立與結案時間、結案備註。

  • 「標記已追回」：已向使用者追回欠款。
  • 「核銷」：金額小於追討成本等原因，由平台吸收損失並列帳。
  • 兩者都需二次確認，備註必填並寫入稽核（wallet_debt.resolve）；已結案的欠款不能再改（INVALID_STATE_TRANSITION）。仍有未結清欠款的帳號無法刪除帳號。

7. 業務規則與狀態機

7.1 清單

draft→active⇄closed→archived

允許的轉換：draft→active、active→closed、closed→active、draft / active / closed → archived。其他一律 VALIDATION_FAILED（TRANSITION）。另有獨立欄位 moderation_status（ok / hidden）；DELETE /wishlists/{id} 的語意是封存。

7.2 捐助（數量型）

reserved→purchased→delivered
  • 允許：reserved→purchased；reserved / purchased→delivered；reserved / purchased→cancelled。其餘回 INVALID_STATE_TRANSITION；只有重複取消是冪等（回 204）；已 delivered 再送 delivered、或對 delivered 做其他轉換，都回 INVALID_STATE_TRANSITION。
  • 改數量只允許 reserved / purchased，且清單須為 active。
  • 誰能標記：捐助者本人；清單擁有者只能在驚喜解鎖後標記「已送達」或取消。
  • 逾期釋放：若清單設了 claim_ttl_hours，捐助時寫入 expires_at；背景工作把逾期的 reserved 設為 expired 並回補數量。進入 purchased / delivered 後 expires_at 清除。
  • 不設 claim_ttl_hours（預設）＝捐助不逾期。創建者介面目前未提供此欄位，需經 API 設定（1–8760 小時）。

超賣防護（為什麼不會多賣）

-- 條件式 UPDATE：同一列在交易內被鎖，只有一筆能讓條件成立
UPDATE wishlist_items SET qty_claimed = qty_claimed + :qty
 WHERE id = :item AND qty_claimed + :qty <= qty_needed
RETURNING qty_needed, qty_claimed;
-- 0 列 → 409 ITEM_FULLY_CLAIMED（附 remaining）
  • 鎖序固定：wishlist_items → claims。改動時不可顛倒。
  • 寫入需 Idempotency-Key（UUID）。占位與業務寫入在同一交易，失敗 rollback 不留痕；24 小時內同鍵同內容回原結果（帶 Idempotency-Replayed），內容不同回 IDEMPOTENCY_CONFLICT。
  • 資料庫以 partial unique index 保證同一人對同一品項只有一筆有效捐助（CLAIM_ALREADY_EXISTS）。

7.4 完成度

唯一定義：sum(已完成單位) / sum(需求單位) × 100，四捨五入；總需求為 0 回 0。數量型 = (qty_claimed, qty_needed)；眾籌型 = 達標（funded / fulfilled）算 1/1，否則 0/1。「已完成項數」為 claimed ≥ needed 的品項數。

冪等建立型 POST（捐助、認捐、營運發點）必帶 Idempotency-Key: <UUID>；缺少回 IDEMPOTENCY_KEY_REQUIRED；重放回應帶 Idempotency-Replayed
並行編輯PATCH 清單 / 品項可帶 expected_updated_at；不符回 409 STALE_VERSION
分頁游標式：?limit=1..100&cursor=…，回 { data: [...], next_cursor }
錯誤RFC 9457 application/problem+json：type、title、status、code、選用的 detail（部分錯誤沒有，例如 404 / 401 / 410 的簡式回應），驗證錯誤另有 errors[]（框架產生的 422 不一定帶）（pointer、code、detail）；限流附 Retry-After
CORS只允許 APP_URL（與 NATIVE_ORIGINS）並帶憑證
安全標頭所有回應加 X-Content-Type-Options: nosniff、Referrer-Policy: no-referrer 等；已自行設定者（如公開清單的 Cache-Control）不覆蓋
唯讀模式read_only 為真時非安全方法回 503 READ_ONLY_MODE
版本策略URL 版本；破壞性變更才升 /v2，v1 至少保留 6 個月並以 Deprecation / Sunset 預告

11.3 CDN 快取與受限清單

路徑讀身分回應CDN

notify::spawn_worker每 5 秒領取到期通知並寄出，失敗最多重試 3 次
ratelimit::spawn_cleanup每 5 分鐘（清理每小時）每 5 分鐘執行 claims::expire_due（釋放逾期捐助）、wishlists::close_due（結束到期清單，並清 CDN）、wishlists::remind_closing（結束前 24h 提醒）、contributions::tick_funding（眾籌截止與 7 天選擇期自動退點）；另每 12 個 tick（約每小時）清理過期冪等鍵（>24h）與限流計數（>2 天）
已知風險任務迴圈若 panic 會靜默終止，而行程仍存活（/healthz 仍 200）。建議加上「逾期捐助未釋放」告警，或讓行程在背景任務結束時退出由 Dokploy 重啟（檢查清單 §0.6）。擴充為多實例前須先確認各任務的冪等性（大多已用列鎖下重檢條件設計）。

11.5 金鑰與備份

  • SHIPPING_ENC_KEY：每個環境各自產生、不共用、不進 repo。遺失 = 所有收件資訊與採購單地址快照永遠無法解密，營運無法寄貨。請備份在至少兩個獨立的地方（密碼管理器 + 離線備份），且不與資料庫備份放在同一處。目前沒有輪替機制（key_version 固定為 1）；要輪替須先實作「多把金鑰依 key_version 解密 + 背景重新加密」，不能直接換環境變數。金鑰外洩時，攻擊者仍須同時取得資料庫才能讀到地址。
  • 這把金鑰同時加密 staff 的 TOTP 密鑰。
  • 現況：尚無任何備份（P0）依 docs/deploy-verification-2026-10-17.md，正式環境已有真實資料寫入，但目前沒有任何資料庫備份，也沒做過還原演練。這是優先級最高的未完成項（docs/TODO.md P0）；另有驗證過程中外露機密的輪替待辦（P1）。以下為目標與建議，尚未達成。
  • 資料庫備份：PRD 目標 RPO ≤ 5 分鐘、RTO ≤ 1 小時。RPO ≤ 5 分鐘需要 WAL 歸檔（pgBackRest / WAL-G → R2）；僅排程 pg_dump 則 RPO 等於備份間隔，須由產品負責人明確取捨。備份目的地應在不同供應商 / 帳號，且至少每季做一次還原演練並記錄實際 RTO。未演練的備份等於沒有備份。
  • R2：incoming/ 前綴不得對外公開（WAF 封鎖 + 1 天生命週期刪除）；API Token 只給該 bucket 的 Object Read & Write。
  • 單點故障：整機掛掉全站掛掉；請預先寫下並計時恢復步驟（新 VPS → Dokploy → 還原 DB → 設環境變數 → Tunnel）。

  • 觸發：PR、push 到 main、每週排程（僅 web-audit）。
  • api：Rust 1.99.0 的 fmt、clippy（warnings 視為錯誤）、測試、覆蓋率（cargo-llvm-cov 0.9.1，版本不符拒絕）、cargo-audit 0.22.2。 mutate：scripts/mutate.sh all（上傳 receipts / patch / logs），不擋 publish-image。

12.3 守則（改動前必讀）

  • 併發防護的回歸測試：改動鎖序或併發相關 SQL（FOR UPDATE / FOR SHARE、ON CONFLICT）時，須在 scripts/mutate.py 補對應 mutant，並確認 scripts/mutate.sh all 全數 killed（還原後 SHA 一致）。輸出在 apps/api/target/mutations/，勿與相同 SQLx test path 的一般測試併跑。
  • 鎖序不可顛倒：捐助 wishlist_items → claims；點數 wishlists(FOR SHARE) → point_wallets(依 id) → wishlist_items → contributions。
  • 餘額只經 points::post；帳本只增不改。
  • 受限內容不得進可快取路徑：GET /public/wishlists/{slug} 不可讀 cookie。清單不再可公開提供時呼叫 cdn::purge_wishlists。
  • 新增後端模組：只改 lib.rs 合併 routes()；錯誤統一走 error.rs 的 problem+json。
  • 新增創建者路由：加進 routeRules；直接 $fetch 的受保護請求要帶 nativeHeaders()。
  • 刪除已覆蓋的程式碼也會改變覆蓋率比例；刻意調整測試範圍時重新量測並更新 baseline（apps/api/tests/coverage-baseline.json），不要當成 flaky。
