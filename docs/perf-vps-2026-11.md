# 低規 VPS 效能評估與優化（2026-11）

目標：在 **1 vCPU / 1 GB RAM、API 與 Postgres 同機** 的主機上，求 5 分鐘內能穩定承受的最大同時在線使用者數，
條件 p95 < 500 ms、p99 < 1 s、錯誤率 < 1%。壓測工具與重現步驟見 `scripts/loadtest/README.md`。

## 結果

每輪都從全新資料庫開始（種子資料後立即壓測），1 分鐘爬升、維持 5 分鐘。

| 版本 | 人數 | p95 | p99 | 錯誤率 | 判定 |
|---|---|---|---|---|---|
| 原始程式（TCP、連線池 10） | 650 | 348 ms | 658 ms | 0% | 通過 |
| 原始程式 | 800 | 1,326 ms | 1,768 ms | 0% | 不合格 |
| 優化後（Unix socket、連線池 5） | **3,450** | 329 ms | 600 ms | 0% | 通過 |
| 優化後 | 3,600 | 516 ms | 893 ms | 0% | 不合格（p95） |
| 再加 session 驗證快取（見下） | **3,600** | 283 ms | 595 ms | 0% | 通過 |
| 再加 session 驗證快取 | 3,800 | 546 ms | 993 ms | 0% | 不合格（p95） |

原始程式約 650–800 人，優化後約 3,450–3,600 人，約 **5.3 倍**。優化後每位使用者同時開著一條 SSE（3,450 條全數維持，0 失敗）。

> 更正：最初版本寫「400 → 3,450（8.6 倍）」。當時的會員劇本讀錯 `GET /wishlists` 的回應欄位（`data`），
> 「我的清單 / 進度」兩個請求從未執行；原始程式的 400 人也是在累積了數十萬筆壓測資料的資料庫上量的。
> 上表為修正劇本後、兩邊都從全新資料庫重新量測的結果。

量的是**來源站最壞情況**：每個請求都打到 VPS。正式環境的公開清單與探索頁有 Cloudflare Cache Rule（`s-maxage=10`），
訪客請求（約占 60% 使用者）大多在邊緣就回應，實際容量會更高。

### 劇本

每位虛擬使用者每 3–8 秒換一頁（約 0.6 req/s/人）。訪客 60%：分享頁（SSR 一次 + 瀏覽器帶 ETag 一次）、`/public/status`、`/me`（401）、
回報瀏覽、一半機率看探索頁。會員 40%：儀表板五個請求、自己的清單與進度、好友的 friends 清單，約 1/5 機率捐助後取消。
資料：3,000 位使用者、6,000 份清單、60,000 個品項。模擬主機以 cgroup 限制 API 與 DB 容器共用 1 顆 CPU、1 GB。

### 逐步改善（優化過程中的爬升測試崩潰點，非 5 分鐘驗收；使用修正前的劇本，僅供相對比較）

| 改動 | p95 開始失控的人數 |
|---|---|
| 原始 | ~400（舊劇本、資料庫已累積大量資料） |
| slug 走索引 + 品項索引 | ~1,200 |
| 瀏覽紀錄非同步 commit、探索頁快取 | ~2,000 |
| `/me` 合併查詢、唯讀旗標快取、`config::get` 免複製等 | ~3,100 |
| mimalloc + LTO、Unix socket、連線池 5（含 SSE，90 秒維持） | ~3,700 |

## 發現與修正（依影響排序）

1. **分享頁整表掃描（最大問題）**。`wishlists.slug` 是 `char(10)`，sqlx 以 `text` 綁參數，`slug = $1` 被轉成 `slug::text = $1`，
   唯一索引用不上。分享頁主查詢平均 45 ms，占 DB 時間 95%。改為 `$1::bpchar`（公開頁、SSE、檢舉、支持品項、組織 / 事件）。
2. **ETag 的 `max(updated_at)` 整表掃描 `wishlist_items`**：刻意含已刪除品項，所以用不上 `deleted_at IS NULL` 的部分索引。
   0064 新增 `(wishlist_id, updated_at)` 完整索引。
3. **每次瀏覽 3 次 fsync**：`POST /views` 原本是兩次限流 upsert + 一次 insert，各自 commit。1 vCPU 主機上後端大多在等 `WALWrite` / `WALSync`。
   改為限流在程序內計數（`ratelimit::allow_local`）、寫入單一敘述並以 `set_config('synchronous_commit','off',true)` 非同步 commit。
4. **每個 SQL 往返的固定成本才是主要開銷**。實測 Postgres 行程 CPU 有一半以上不是查詢執行，而是協定、快照與行程切換；
   API 端也有約 30% 在 socket 系統呼叫。因此：`GET /me` 5 次查詢合為 1 次；分享頁的 `has_support` 併入主查詢；
   探索頁（每位訪客都一樣）程序內快取 10 秒；`read_only` 旗標（每個寫入與 `/public/status` 都讀）快取 1 秒，admin 改旗標立即失效。
   兩者由 `MICRO_CACHE` 控制，測試用的 `Config::dev()` 為關。
5. **`config::get()` 每次複製整份設定**（含多個字串與 S3 / 綠界設定，每個請求呼叫多次，品項圖片網址每項一次）：改回傳 `&'static Config`。
6. **glibc malloc 占 API 約 15% CPU**：改 mimalloc，API 常駐記憶體由約 150 MB 降到 30–70 MB；release 開 LTO、`codegen-units = 1`。
7. **公開 SSE 上限 2,000 先於 CPU 成為人數上限**：實測每條約 10 KB，放寬到 5,000。
8. 連線池可由 `DB_POOL_MAX` 調整：1 vCPU 上 5 條比 10 條延遲更低（同 3,300 人 90 秒：p95 269 ms 對 421 ms）。

所有修改都通過完整後端測試（109 個 suite）、`cargo fmt`、`clippy -D warnings`；新增 `tests/micro_cache.rs` 驗證快取的過期與失效。

## 取捨

- 瀏覽紀錄非同步 commit：主機當機（不是程式崩潰）時最近約 0.6 秒的瀏覽紀錄可能遺失；一致性不受影響。捐助、金流等業務寫入完全沒動。
- 瀏覽紀錄改為程序內佇列批次寫入（每 500ms 或 200 筆）：程序結束或佇列滿（1 萬筆）時最多遺失約 0.5 秒的紀錄，端點不再占用連線。
- 瀏覽限流改在程序內：重啟歸零、多實例時各算各的（換版瞬間最多兩倍）。它只擋灌水，不是安全邊界；IP 也因此不再寫進 `rate_limits`。
- 探索頁最多晚 10 秒（與 CDN 原本的 `s-maxage=10` 相同）；`read_only` 在其他實例最多晚 1 秒生效。

## 部署建議（不需改程式，Dokploy 設定）

1. **API 經 Unix socket 連 DB**：在 Dokploy 把 `db` 的 `/var/run/postgresql` 掛成具名 volume，同一個 volume 掛進 `api`，
   `DATABASE_URL=postgres://wishly:<密碼>@localhost/wishly?host=/var/run/postgresql`。實測同負載吞吐 +13%、p95 減半
   （TCP 經 Docker bridge 的 conntrack / veth 開銷在 1 vCPU 上很明顯）。
2. `DB_POOL_MAX=5`。
3. Postgres（1 GB 主機）：`shared_buffers=256MB`、`effective_cache_size=512MB`、`work_mem=4MB`、`max_connections=30`、`jit=off`。
4. cloudflared 直接指向 API 容器，不要再經 Dokploy 的 Traefik（每個請求少一層代理的 CPU）。
5. 維持 Cloudflare 對 `/api/v1/public/*` 的 Cache Rule（已於 2026-10-17 建立）；這是訪客流量最大的槓桿。

## session 驗證快取（後續加入，0065）

每個登入請求都要查一次 `sessions`（約占全部 SQL 敘述的 23%）。成功的驗證改為在程序內快取（`session.rs::cache`，`SESSION_CACHE`）：

- 只快取「有效、未停權」的結果；失敗、停權一律每次查 DB。
- **失效靠 DB trigger，不靠 TTL**：sessions（撤銷、MFA、縮短期限、刪除）、users（停權、刪除、staff、TOTP）與 `staff_mfa_required`
  變更時 `pg_notify('session_inval')`，每個實例的 listener 收到就清空。撤銷路徑散在十幾處（登出、撤銷裝置、改密碼、停權、刪帳…），
  做在 DB 層才不會漏，也涵蓋手動 SQL 與多實例。續期（`last_seen_at`、延長 `expires_at`）刻意不觸發。
- 查 DB 前記下失效世代、寫回時世代已變就丟棄，避免 commit 前讀到舊值的請求在清空後寫回。
- LISTEN 未連上（含斷線重連期間）完全不用快取；TTL 30 秒只是保險。MFA 與 session 期限存時間點，快取中的項目準時過期。
- 殘餘風險：撤銷 commit 到 listener 收到通知之間（同機約毫秒級），同一個權杖仍可能被放行。

同一時段、同一個執行檔 A/B（3,600 人、5 分鐘）：

| | p95 | p99 | 5 分鐘處理請求數 |
|---|---|---|---|
| 關閉（`SESSION_CACHE=0`） | 1,059 ms | 1,746 ms | 558,826 |
| 開啟 | 283 ms | 595 ms | 642,632（+15%） |

（關閉時的 p95 比先前同條件的 516 ms 高，是不同時段主機效能的差異；同一時段的 A/B 才有可比性。）

## 第二輪：固定開銷與缺漏索引（2026-11-13）

改動：

- 連線池 `test_before_acquire(false)`（sqlx 預設每次取連線先 ping 一次），並設 `max_lifetime` 30 分鐘、`idle_timeout` 5 分鐘。
- 兩條 `LISTEN`（session 快取失效、SSE 匯流排）改用自己的連線（`dashboard::pg_listener`），不再長期各佔連線池一條。
  **`DB_POOL_MAX=5` 現在 5 條都給請求用**（原本實際只有 3 條）。
- 公開清單的 SSE 不做每 60 秒的定期重驗（原本每條連線每分鐘白查 2 次；改成非公開後會恢復）。
- 通知 worker 閒置時逐步放慢到 5 秒輪詢一次，有工作立刻回到每秒。站內通知在閒置後最多晚 5 秒出現；驗證碼信不走 outbox，不受影響。
- CORS 預檢結果快取 2 小時。
- 分享頁：沒有登入線索（`ws_hint`）也沒有訪客權杖的匿名訪客不再打 `/me`、`/guest/me`（原本各吃一個 401）；OAuth 導出前先設線索。
- 0075：`wishlists(event_id)`、`wishlists(org_id)`、`receipts(item_id, …)`、`receipts(wishlist_id)`（事件頁、組織頁、據點列表、實收原本整表掃描）。
- `/admin/wishlists` 的 slug 比對補上 `::bpchar`。

量測（macOS / OrbStack，API 與 DB 綁同一顆核心，3,600 人、30 秒爬升 + 90 秒維持，同機 A/B）：

| | 總 CPU（API + DB） | 每請求 CPU | p95 |
|---|---|---|---|
| 改動前 | 53.0 s | 211 µs | 1.7 ms |
| 改動後（同劇本） | 52.4 s | 208 µs | 1.7 ms |
| 改動後（訪客不打 `/me`） | 53.4 s | — | 2.0 ms |

**在這份劇本下量不出差異**（約 1%，與每輪之間的誤差同級）。把 CPU 配額壓到 0.3 核、3,400 人時兩版都頂到配額，
p95 在 100–220 ms 之間隨機擺盪（同一版重跑就差一倍），同樣分不出高下，也沒有退步。原因：

- ping 是一次真的往返，但 Postgres 處理一個 Sync 幾乎不花 CPU，省下的只有 API 端每請求約 6 µs。
- 匿名的 `/me` 401 不查資料庫，少打它省的是網路與連線，不是 CPU。
- SSE 定期重驗在 90 秒的測試裡只發生一次；通知 worker 的輪詢只在閒置時才占比高。
- 索引與後台 slug 修正影響的是事件頁、組織頁、實收、後台搜尋，劇本沒有涵蓋。

所以這一輪的價值在「資料量變大後不會整表掃描」、「閒置時不空轉」與「連線池吃緊時多兩條可用」，不是每請求 CPU。
每請求約 210 µs 的 CPU 由 API 與 Postgres 各占一半，要再提高人數得從實際的查詢與序列化工作下手。

## 第三輪：往返合併、後台保護、前端請求量（2026-11-13）

同機 A/B（條件同第二輪，3,600 人，各跑兩輪，錯誤率皆 0）：

| | 每請求 CPU | 總 CPU（API + DB） | p95 |
|---|---|---|---|
| 第二輪 | 237 / 242 µs | 52.6 / 53.4 s | 1.8 / 2.0 ms |
| 第三輪 | 230 / 239 µs | 51.1 / 52.7 s | 1.8 / 2.0 ms |

整體差 1–3%，與每輪之間的誤差同級：**沒有退步，也沒有量得出來的整體提升**。逐項看 `pg_stat_statements`：

量得到的：

- 瀏覽紀錄批次寫入：29,897 次往返 / 1,495 ms → 321 次 / 618 ms（DB 時間 −59%，且端點不再占用連線）。
- 站內通知列表 + 未讀數：兩次往返（390 + 315 ms）→ 一次（689 ms）。DB 時間持平，少 9,200 次往返。

量不到的（劇本有涵蓋，數字沒變）：

- `access::viewer` 寫回 session 快取：session 查詢仍是約 5,850 次。這些查詢是每個 session 首次驗證加上 30 秒 TTL 到期重驗，
  不是 viewer 路徑漏快取；改動對「同一人短時間連開多個受限清單」才有效，劇本裡幾乎沒有。
- 儀表板少一次日期查詢：該查詢原本就排不進前 28 名。

劇本沒有涵蓋、屬於保護性質的（沒有實測數字）：

- 後台統計 / 金流聚合 60 秒快取、後台查詢 8 秒 `statement_timeout`：防止營運人員的重查詢占住連線池。
- 圖片解碼並行 4→2、單張上限 128 MiB：1 GB 記憶體下的 OOM 保護。
- 個人頁關係判斷合併（往返 9→8 / 10→9）、對外 HTTP client 共用、限流 upsert 非同步 commit。
- 前端：好友申請數、導覽狀態、staff 驗證、`/public/status` 的重複請求；SSE 重連抖動。k6 直接打 API，量不到前端省下的請求。

壓測排行第一的儀表板認捐名單查詢（平均 373 µs）是壓測資料的假象：`claims` 表從空表開始、只有約 1,800 列，
規劃器選整表掃描；正式資料量下會走 `claims_item_idx`。不需處理。

結論：每請求 CPU 約 235 µs、API 與 Postgres 各半的結構三輪都沒有變。熱路徑（分享頁主查詢、品項查詢）每次 33–50 µs，
已經沒有單點可省；要再提高同時人數，靠的是 CDN 命中率與少發請求，不是再併查詢。

## 尚未做、可再提升的

- 分享頁的品項查詢併入主查詢（每次完整載入少一次往返）、好友 / 封鎖判斷合併。
- 分享頁 JSON 改用 `#[derive(Serialize)]` 結構直接序列化，取代 `json!` 建樹（API 端 CPU 的一部分）。
- 儀表板的認領人數、認捐名單、贊助名單三個查詢合併（每次載入少兩次往返）。
