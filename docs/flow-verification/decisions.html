待決事項：規格與實作不一致

流程驗證過程中，凡是「改規格或改程式都說得通」、或需要產品 / 法遵判斷的項目都記在這裡，不擅自修。每項附建議；決定後再依結論改程式或改 02 文件。

Q1 · 擁有者能否把「已送達」改回取消？ 待決

規格F5 狀態機：delivered → cancelled「僅 owner 或 coordinator 更正誤標」，並回補 qty_claimed。
現況claims.rs 一律禁止，owner_claim_actions.rs 斷言 409；04 契約也寫「已 delivered 不可取消」，所以是 02 與 04 互相矛盾。進度頁「標為已送達」無確認框。
影響擁有者誤點「標為已送達」後無法撤回，該品項永遠被算作已送達、不會釋出給其他人。
選項A. 照規格開放 owner 取消 delivered（並回補）。
B. 維持禁止，但在「標為已送達」加二次確認，並更新規格。
C. 新增 owner 專用「退回已購買 / 已捐助」而非取消。
建議B：改動最小、避免「送達後又取消」讓捐助者困惑；若常有誤標再做 C。

Q2 · 清單關閉後，捐助者還能取消 / 標已購買嗎？ 待決

規格F8 狀態表：closed 時「guest 不可改量 / 取消捐助」，owner 仍可標 delivered 與取消；F5 錯誤碼 WISHLIST_CLOSED「清單 closed / archived 後，guest 不可再改量或取消」。（規格寫於 D50 之前，「guest」即捐助者。）
現況改量已擋（409）；取消、標 purchased / delivered 仍可（實測 closed 清單上 DELETE 回 204）。
影響關閉後捐助者取消會讓已結束清單的完成度往下掉；但禁止取消也代表捐助者無法撤回已無法履行的承諾。
選項A. 照規格：closed 後捐助者的取消回 409，標 purchased / delivered 仍允許（推進履約）。
B. 維持現況並改規格（關閉只停止新捐助與加量）。
建議B：捐助者在活動結束後仍需能標「已送達」與撤回；請確認。

Q3 · 已購買的捐助能改數量嗎？ 待決

規格F5「改量 PATCH quantity（僅 reserved 可改）」。
現況reserved 與 purchased 都可改量（加量同樣走條件式 UPDATE，不會超賣）。
補充04 契約寫「qty 只能在 reserved / purchased 時改」，與實作一致，只有 02 落後。
建議維持現況，併入 Q6 更新 02。

Q4 · 「每人每清單有效捐助最多 30 筆」上限 待決

規格F4 步驟 5：每使用者每清單有效 claim 上限 30。
現況沒有「有效筆數」上限，改為限流：同清單每小時 15 次、每人每小時 30 次（429）。長期來看同一人仍可在一份清單累積任意多筆。
建議維持限流並在規格註明取代（每品項本來就只能有一筆有效捐助，上限等同品項數）；若擔心洗單再補 DB 計數上限。

Q5 · 完成度百分比的定義 待決

規格F7：completion_pct = items_done / items_total（主數字），claimed_pct 為數量比例。
現況公開頁、儀表板都以數量比例為主數字（例：2 品項、數量 3/4 → 顯示 75%，同時顯示 1 / 2 項）。有測試固定此行為（unified_pct…）。
建議更新規格為現況（數量比例對送禮者較直觀）。

Q7 · SSE 每 IP 同時連線上限：5 還是 16？ 待決

規格F3 / 6.2：每 IP 同時 5 條，超過 429。
現況dashboard.rs MAX_SSE_PER_IP = 16（另有全域 2000），實測第 17 條起回 429；commit 74b3ddc 未說明為何不是 5。
考量台灣行動網路大量使用電信 CGNAT，同一出口 IP 後面可能有很多人；辦公室 / 家庭也共用 IP。上限太低時，同一個人開兩三個分頁加上家人一起看就會被拒，前端退回輪詢（仍可用，但即時性下降）。
建議維持 16 並更新規格；若要防濫用，交給 Cloudflare 邊緣的「SSE 新連線每分鐘每 IP 10 次」規則。

Q8 · 驚喜清單是否要對訪客顯示提示？ 待決

規格F3：「公開頁顯示『這是驚喜清單』提示」。03 線框沒有畫。
現況未實作。擁有者看到「驚喜模式中」遮罩；訪客端完全沒有提示。
影響送禮者不知道這是驚喜，可能在聊天或留言中提前透露。
建議在分享頁標題下加一行提示，例如「這是驚喜清單：活動日前建立者看不到誰送了什麼，請先別透露喔」。需要你確認文案後我再實作（含 en / vi）。

Q9 · 清單擁有者沒有設定帳號代號時，非好友如何加好友？ 待決

規格F21：FRIENDS_ONLY 時「前往個人頁加好友」。
現況只有擁有者有 handle 才出現按鈕；handle 可為空（預設為空），此時門檻頁只剩「回首頁」，對方完全沒有下一步。
選項A. 無 handle 時顯示「請向 {name} 索取好友邀請連結」說明。
B. 門檻頁直接提供「送出好友申請」（後端已有 POST /friends/requests，但需要可定址的對象：可讓 403 回應帶不可猜的 user id，或新增「對清單擁有者申請」端點）。
建議先做 A（只改前端文案，0 後端改動），B 視需求再議。
