結論

缺陷與處置

B1 · 路人 PATCH / DELETE 別人的捐助回 403 已修正

規格（F5 權限矩陣、授權實作原則）：非本人一律 NOT_FOUND，避免洩漏資源存在。實作回 403 FORBIDDEN「只有捐助者本人可以操作」，可用來探測任意 claim id 是否存在。

修正：apps/api/src/claims.rs 非本人、非擁有者改回 AppError::NotFound；擁有者在驚喜鎖定期間或做非允許操作仍回 403（屬「已登入但角色不足」）。調整 3 個既有測試的預期值。

B2 · 同一目標狀態重送回 409，UI 連點跳錯 已修正

重現：/me/claims 快速點兩下「標記已購買」→ 第二個請求回 409 INVALID_STATE_TRANSITION，橫幅顯示「不允許的狀態轉換」。規格 F5 冪等性：目標狀態與現況相同 → 200 並回目前資料。

修正：狀態轉換表加入「同狀態 no-op」，不重寫時間戳、不寫第二筆 audit。E2E 以同步雙擊並記錄兩個 PATCH 都回 200；已驗證把修正還原後此測試會失敗。

B3 · 只改備註會重設 purchased_at 已修正

修 B2 時發現：UPDATE claims 的 purchased_at / delivered_at / cancelled_at 只看目標狀態，對已購買的捐助改備註（status 不變）會把 purchased_at 改成現在。修正為「狀態真的改變才寫入」，由 same_status_patch_is_idempotent_and_keeps_timestamps 覆蓋。

B4 · 非擁有者開進度頁顯示「連線失敗」 已修正

API 正確回 404，但 404 的 problem 沒有 detail，useApi 一律退回「連線失敗，請稍後再試」，使用者會以為是網路問題而重試。修正：沒有 detail 的 404 改顯示「找不到這個項目，可能已被刪除或你沒有權限」（三語），影響所有創建者頁。E2E flow-f05 #3、vitest 覆蓋。

B5 · 英文 / 越南文介面顯示中文錯誤 Issue #29 已修（4437cc1）

後端 detail 只有中文，前端 29 個頁面 / 元件直接顯示。範圍跨前後端、需選方案，故開 #29 而非在此修。

後續：#29 由另一個工作階段修正（前端依錯誤碼翻譯，5xx 不顯示後端 detail，commit 4437cc1）。稽核結果：

  • 提交歸屬：#29 的初始修正（useApi.ts、useGuest.ts、utils/errors.ts、tests/apiErrorLocale.test.ts、tests/setup.ts）因 W1 提交時用了 git add -A，被併進 1a1f187（訊息只寫裝置驗證）。內容本身無誤且 4437cc1 建立在其上，不改寫歷史；之後一律以明確路徑提交。
  • E2E 回歸：4437cc1 未跑瀏覽器 E2E，造成 3 個失敗。其中 2 個（後台現金退款、眾籌可見度儲存失敗）是測試仍期待顯示 500 的後端 detail，屬預期行為改變，已更新斷言；1 個是 SERVICE_UNAVAILABLE 被翻成「驗證服務暫時無法使用」——後端目前只有 Turnstile 用這個碼，但 02 規格也用它表示連線池耗盡 / lock_timeout 等一般 503，在認捐表單出現「驗證服務」會誤導，已改為通用的「服務暫時無法使用」（三語）。修正後全套 E2E 157 / 157 通過。

根因追查：503 文案（側邊審查提醒，2026-10-22）

提醒的現象正確（一般 503 被說成「驗證服務」），但「資料庫忙碌時也回 SERVICE_UNAVAILABLE」與程式不符。實際根因有兩層：

  1. 通用錯誤碼被拿來表示特定故障：後端唯一回 SERVICE_UNAVAILABLE 的地方是 Turnstile siteverify 連不上（reports.rs，檢舉與 OTP 人機驗證共用）。#29 翻譯時只看得到這個用法，於是把通用碼寫成「驗證服務」。前端無從分辨，只改文案會讓 Turnstile 故障變得含糊。
  2. 資料庫壅塞根本沒有回 503：AppError::Db 一律 500 INTERNAL_ERROR、無 Retry-After；連線池也沒設 acquire_timeout（sqlx 預設 30 秒），尖峰時請求會卡 30 秒才失敗。02 §6.4 要求 3 秒內回 503 + Retry-After、不排隊堆積。

修正：

  • 後端：Turnstile 連不上改用專屬碼 CAPTCHA_UNAVAILABLE（503）；連線池 acquire_timeout = 3s；連線池逾時、lock_timeout（55P03）、statement_timeout（57014）對應 503 SERVICE_UNAVAILABLE + Retry-After: 2，其他資料庫錯誤維持 500。
  • 前端文案：SERVICE_UNAVAILABLE →「系統忙碌中，請稍後再試」；新增 CAPTCHA_UNAVAILABLE →「人機驗證服務暫時無法使用，請稍後再試」（zh / en / vi）。
  • 契約：04 錯誤碼表與 TS 型別、02 錯誤碼表補 CAPTCHA_UNAVAILABLE，並寫明 SERVICE_UNAVAILABLE 是通用碼。
  • 測試：db_overload.rs（真的把只有 1 條連線的 pool 占住 → 503 + Retry-After；製造 lock_timeout → 503；其他錯誤 500）、config_mail.rs 斷言 CAPTCHA_UNAVAILABLE、vitest 三語各驗兩種 503 文案不可混用、guest-errors E2E 改驗「系統忙碌中」。

未做：02 要求的 lock_timeout=2s、statement_timeout=5s、idle_in_transaction_session_timeout=10s 目前沒有設定，見 Q11。

B15 · 進度頁較早的重抓晚到時，會把畫面蓋回舊狀態 已修正

追查 flow-f05「擁有者取消捐助」在全套並行時偶發失敗的根因（先前只修了測試的對話框處理，治標）：進度頁有兩個重抓來源——操作後的 load() 與 SSE 事件 debounce 500ms 的 load()——彼此重疊時以「最後回來的回應」為準。若 SSE 觸發的請求在取消前送出、卻在取消後的重抓之後才回來，畫面會退回「已捐助」，直到下一個事件才恢復；擁有者會以為取消沒成功而再按一次。

修正：progress.vue 為每次 load() 編號，只套用最後一次發出的請求結果。新增 E2E 以 route 攔截讓較早的 dashboard 回應確定最後才到：拿掉修正時失敗（畫面變回「已捐助」），修正後三種裝置 × 3 次共 36 次通過。

裝置與解析度

新增的 flow-* E2E 已加入 mobile（iPhone 13，390×664、觸控）與 tablet（iPad gen 7，810×1080）兩個 project，三種裝置皆通過。另以 Playwright 在 320 寬、iPhone 13、iPad Mini 直式、iPad 橫式、1280、1920 六種解析度掃描 /s/{slug}、/me/claims、/lists/{id}/progress：檢查水平捲動與超出視窗的元素（皆無），並逐張看截圖。

B9 · 我的捐助：狀態徽章與「誰看得到」黏在一起 已修正

手機寬度（320 / 390）下，「已捐助」徽章自成一行且帶左邊距，緊接著「誰看得到」沒有間隔，看起來像同一個標籤。改為徽章接在品名後（與其他頁一致），可見度選單獨立一行。
